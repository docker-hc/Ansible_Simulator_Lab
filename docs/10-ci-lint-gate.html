01Why this exists

scripts/lint-check.sh has always returned a non-zero exit code when a check fails — but nothing enforced that. It was run by hand at checkpoint time, so a tired push could still land un-linted YAML, a broken playbook, or a shellcheck violation on main. "Advisory" meant the script was honest; it just had no teeth.

This work gives it teeth: lint-check.sh now runs in GitHub Actions on every push and pull request, and a repository ruleset makes that run a required status check on main. Code that fails the gate cannot be merged. The gate covers all seven checks — yamllint, ansible-lint, ansible --syntax-check, ansible-inventory --graph, vault-encrypted, vault-pass-not-tracked, and shellcheck.

A sibling task confirmed commit hygiene (no tracked __pycache__/*.pyc, no trailing whitespace in 08-export-facts.yml, all .gitignore guards present) via scripts/verify-commit-hygiene.sh, which is built to slot into CI later as a second gate.

Pinned toolchain (keep CI == desk)

The workflow pins the exact versions the mgmt node runs, so CI green/red matches local:

ansible-core   == 2.16.18
ansible-lint   == 26.4.0
ansible-compat == 26.3.0
yamllint       (latest)        # required by lint-check.sh
shellcheck     (runner-provided)
Pin discipline

When you bump ansible-lint on the mgmt node, update the pin in ansible-lint.yml (and re-pin ansible-compat) in the same change — otherwise CI silently drifts from your desk. pip will error loudly if the two ever conflict, which is the behaviour you want.

03How a change flows

The vault is the subtle part. Three of the seven checks have to decrypt group_vars/vault.yml just to parse the playbooks, so CI needs the key — which it gets from the secret, not from the gitignored /root/.vault_pass (absent on the runner).

  1. You open a PR into main (direct pushes are blocked by the ruleset).
  2. The workflow triggers; it installs the pinned toolchain and the collection.
  3. The Run lint gate step writes the ANSIBLE_VAULT_PASSWORD secret to a temp file and sets ANSIBLE_VAULT_PASSWORD_FILE to its path.
  4. That env var overrides the vault_password_file = /root/.vault_pass line in ansible.cfg (env beats the ini) — and propagates into the ansible-playbook --syntax-check subprocesses that ansible-lint spawns.
  5. lint-check.sh runs all 7 checks; the temp file is wiped by a trap on exit.
  6. If any check fails, the job exits non-zero → the required check goes red → the PR can't merge.
Why the env var, not a file

ANSIBLE_VAULT_PASSWORD_FILE names a path to a file containing the password. CI writes that file at runtime from the secret; the YAML never contains the password itself. PRs from the repo receive the secret, so the vault checks pass on PRs. (Fork PRs do not receive secrets — irrelevant for a solo/private repo, but worth knowing if you ever accept external contributions.)

04What to do — operating

Everyday change (the new flow)

Because main is now PR-only, "commit and push to main" is replaced by:

git checkout -b my-change
# only if editing playbooks/scripts/roles (Doc 9 lock):
sudo ./scripts/harden-lab.sh --unlock
# ...edit...
git add . && git commit -m "..."
git push -u origin my-change
gh pr create --fill
# ansible-lint runs on the PR; once green:
gh pr merge --squash
sudo ./scripts/harden-lab.sh --lock      # re-baseline if you unlocked
Branching · create vs. rename

Two commands that look alike but aren't:

git checkout -b <name> creates a new branch and switches to it — how you start a change.
git branch -m <name> renames the branch you're already on, in place. It does not create a branch, so you don't follow it with another checkout -b — that would just make a redundant third branch.

After a rename, git branch --show-current confirms where you are. Name branches after the change (docs/ci-lint-gate), not the repo — a branch named like the repo is confusing in the PR list.

Pull requests · what they are & what "green" means

A pull request (PR) proposes merging your branch's commits into main. The name is backwards — you're offering changes, not pulling them (GitLab's term, "merge request", is clearer). On GitHub it's a page showing the diff, a review area, and the status of any automated checks.

You need one because the ruleset blocks direct pushes to main: a PR is the only path in, and it's the one place the required ansible-lint check gets to run and gate the merge. Opening or pushing to a PR fires the workflow (it's wired on: pull_request), and the job reports a status back onto the PR — green ✓ = all 7 checks passed, red ✗ = something failed, a spinner = still running.

Because the check is required, the merge button stays disabled until it's green. So "once it's green" simply means the check finished and passed — at which point you merge it yourself (gh pr merge --squash; 0 approvals needed). Think of the PR as a holding area where your change is auto-vetted, and main only accepts it after the vetting comes back clean.

Rotate the vault password

Change it in both places or CI will fail to decrypt:

# 1. on the mgmt node, update the file ansible.cfg points at
# 2. re-set the GitHub secret (interactive prompt avoids shell history):
gh secret set ANSIBLE_VAULT_PASSWORD --repo docker-hc/Ansible_Simulator_Lab

Emergency bypass

The ruleset currently allows no bypass (current_user_can_bypass: never) — even the owner goes through PRs. If you need a break-glass path, add the Repository-admin role to the bypass list: Settings → Rules → Rulesets → main-lint-gate → Bypass list.

Pending maintenance

CI annotates that actions/checkout@v4 and actions/setup-python@v5 run on Node 20, which GitHub is forcing to Node 24 by default from 16 Jun 2026. Non-blocking, but bump them to current major versions in ansible-lint.yml before then to silence it.

05Troubleshooting & lessons

Each of these actually happened while standing the gate up. They're the failure modes most likely to recur.

Symptom · cd: /etc/ansible/Ansible_Simulator_Lab: No such file or directory

Cause: lint-check.sh hardcoded an absolute lab path; the runner checks the repo out elsewhere.
Fix & lesson: resolve the repo root dynamically — LAB="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)". Any script that runs in CI must not assume a lab-specific path.

Symptom · SC2034 LAB appears unused

Cause: the dynamic-root edit left the old LAB= assignment orphaned; the gate's own shellcheck step caught it.
Fix & lesson: keep LAB both assigned and read (cd "$LAB"). The shellcheck check polices lint-check.sh itself — the gate guards its own gatekeeper.

Symptom · ERROR! The vault password file /root/.vault_pass was not found

Cause: three checks decrypt group_vars/vault.yml; the runner has no vault file.
Fix & lesson: supply the password through a GitHub secret + ANSIBLE_VAULT_PASSWORD_FILE env override (see §03). Any check that decrypts needs the key present in CI; checks that only inspect the file (vault-encrypted header, vault-pass-not-tracked) do not.

Symptom · HTTP 422: Secret names can only contain… (on gh secret set)

Cause: the gh secret set NAME < file stdin-redirect form tripped a name-parse quirk.
Fix: use the interactive prompt (gh secret set NAME, paste at the hidden prompt) or --body "$(cat file)". The prompt also keeps the password out of shell history.

Design note · why a required check needs a PR rule

Required status checks only gate merges via pull request. A direct push to main would run the check but wouldn't be blocked by it. That's why the ruleset also requires a PR (with 0 approvals): it forces every change through the one path where the check can act as a gate.

06Verifying it's live

# ruleset present and active
gh api repos/docker-hc/Ansible_Simulator_Lab/rulesets --jq '.[].name'
# -> main-lint-gate

# latest CI run status
gh run list --workflow=ansible-lint.yml --limit 3
# -> top row: completed / success

# commit hygiene (item 3) on demand
./scripts/verify-commit-hygiene.sh
# -> ALL CHECKS PASSED
Done state

Item 3 verified clean. Item 2 live: lint-check.sh is a required check on main, vault-aware in CI, and lint-check.sh itself is now path-portable for the prod host. The drawer is locked and the only key is the GitHub secret.

07Command reference

Every command used to build and operate the gate, grouped by task — what each does and when you reach for it.

Branches & pull requests

CommandWhat it does / when
git branch --show-currentPrints the branch you're on. Sanity-check this before you commit.
git checkout -b <name>Creates a new branch off the current one and switches to it. Start every change this way.
git branch -m <name>Renames the branch you're already on, in place. Does not create a new branch — so it isn't followed by another checkout -b.
git switch <name>Switches to an existing branch (e.g. git switch main).
git push -u origin <name>Pushes the branch and sets it to track origin. The -u is only needed on the first push; afterwards just git push.
gh pr create --fillOpens a PR, using your commit message as the title/body.
gh pr checksShows the status of the PR's checks — i.e. whether ansible-lint is green yet.
gh pr merge --squashMerges the PR as one squashed commit, once the required check passes.
git switch main && git pullAfter the merge, return to main and pull the merged change.

Running & watching the gate

Hardening lock rhythm (Doc 9)

CommandWhat it does / when
sudo ./scripts/harden-lab.sh --unlockMakes playbooks/scripts/roles writable. Run before editing any of them.
sudo ./scripts/harden-lab.sh --lockRe-locks read-only and re-baselines checksums. Run last in a checkpoint.
sudo ./scripts/harden-lab.sh --statusShows the current lock state.

Note · docs/ is not locked

Adding HTML to docs/ needs no unlock — only playbooks, scripts, and roles are in the lock set. Editing any of the gate's scripts, though, follows the unlock → edit → commit → lock rhythm.

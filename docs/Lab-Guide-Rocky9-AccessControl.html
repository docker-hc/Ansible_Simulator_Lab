Access Control
& Production Roles

Moving from "one root does everything" to production role separation — who may edit automation, who may run it, and how every action stays attributable. Two enforcement layers: Git review for changing the code, OS groups and scoped sudo for running it on the box.

01 Why role separation

In the lab, a single root account does everything: edits playbooks, runs them, holds the vault, reaches the arrays. That is fine for one person building a sandbox. In production it fails three ways at once — an accidental edit has nothing to stop it, an over-privileged colleague can change automation unreviewed, and a compromised account owns the whole estate. Role separation answers a single question for every action: is this person authorized to do this, and can we prove who did it?

The three pillars
Authorization — each person can do only what their role permits. Attribution — every change and every run is tied to a named individual. Recovery — any unwanted change can be reverted from an off-box source of truth. Git, groups, and sudo together deliver all three; no single one is sufficient.

The guiding rule throughout is least privilege: grant the minimum capability a role needs, nothing more. An operator who runs reports does not need to edit playbooks; an author who edits them does not need to deploy to production unreviewed.

02 The four roles

Production storage-automation typically resolves into four roles. One person may hold several, but the rights stay separate so no single uncontrolled action can both change automation and run it against production.

RoleMay edit codeMay run on prodMay approve/mergeMay read
OperatorNoYes (scoped)NoYes
Author / engineerVia PR onlyNoNoYes
Approver / leadVia PRYesYesYes
AuditorNoNoNoYes
  • Operators execute known-good automation against the arrays; they cannot change what it does.
  • Authors propose changes through pull requests; they cannot merge their own work or deploy it.
  • Approvers/leads review and merge, and hold production deployment rights — the decision of what becomes live.
  • Auditors see everything (code, history, logs) and change nothing.

03 Two enforcement layers

Authorization lives in two places, and both are needed. The Git layer controls who can change the automation; the OS layer controls who can run it on the box. A person could be allowed to edit code in Git but not run it in production, or run it but never edit it — the two layers are independent on purpose.

QuestionEnforced byMechanism
Who can change a playbook?Git layerBranch protection + required PR review + CODEOWNERS
Who can run a playbook on prod?OS layerUnix groups + scoped sudo on the mgmt node
Who did what, when?BothSigned commits + named accounts + sudo logs
The cardinal rule
The production box is a read-only deployment target, never an editing surface. Nobody edits playbooks directly on the mgmt node. Changes happen in Git, get reviewed, merge to main, and the box pulls the result. This single inversion is what makes the whole model enforceable — if no one edits on the box, the only way to change automation is through the reviewed Git path.

04 Git layer: PR review

Modern "authorized to edit" lives in Git. The repository is the source of truth; production pulls from it. Changes flow through pull requests so that editing and approving are separate acts by separate people.

Teams map to roles

On GitHub (or GitLab) create teams that mirror the roles, and add people to them:

TeamRepo permissionCan do
storage-engineersWritePush branches, open PRs — cannot merge to main
storage-leadsMaintainReview, approve, merge; manage branch settings
storage-operatorsReadClone/pull; run on the box (OS layer), no code change
storage-auditorsReadView code, history, PRs — nothing else

The branch model

Engineers never commit to main directly. They branch, push, and open a PR:

engineer's workstationgit
git checkout -b feature/add-gad-playbook
# edit playbooks/...
git commit -S -m "Add GAD provisioning playbook"   # -S = signed
git push origin feature/add-gad-playbook
# open a PR on GitHub → review → approve → merge to main

The -S flag signs the commit with the author's GPG/SSH key — cryptographic proof of who wrote it. Require signed commits in branch protection (next section) so unsigned commits are rejected.

05 Branch protection & CODEOWNERS

Branch protection is what makes review mandatory rather than optional. On GitHub: Settings → Branches → Add branch protection rule for main:

  • Require a pull request before merging — blocks all direct pushes to main.
  • Require approvals (at least 1, often 2) — a PR cannot merge without sign-off.
  • Dismiss stale approvals on new commits — re-review if the code changes after approval.
  • Require review from Code Owners — ties approval to the right team per path.
  • Require signed commits — rejects unsigned history.
  • Require status checks — lint/CI must pass before merge (your lint-check.sh as a CI job).
  • Do not allow bypassing — applies the rules even to admins.
  • Restrict who can push — only storage-leads may merge.

CODEOWNERS — approval by path

A .github/CODEOWNERS file requires that changes to specific paths get approval from a specific team. This is how you say "changes to production playbooks need a lead's sign-off":

.github/CODEOWNERS
# default owner for everything
*                       @org/storage-leads

# production playbooks & scripts need a lead
/playbooks/             @org/storage-leads
/scripts/               @org/storage-leads

# roles can be approved by engineers or leads
/roles/                 @org/storage-engineers @org/storage-leads

# vault & CI config: leads only
/group_vars/vault.yml   @org/storage-leads
/.github/               @org/storage-leads
CI as a gate, not just a check
Wire scripts/lint-check.sh into a GitHub Actions workflow that runs on every PR. Make it a required status check in branch protection. Now a change that fails the 7-gate lint physically cannot merge — the same quality bar you use locally becomes an enforced production gate.

06 OS layer: groups & users

The Git layer controls the code. The OS layer controls execution on the mgmt node. The foundation is the elimination of shared root: named accounts only, role groups, and a service account that actually owns the project.

Service account owns the automation

mgmt noderoot
# unprivileged service account that owns and runs the automation
useradd -r -m -d /home/svc-ansible -s /bin/bash svc-ansible

# role groups
groupadd storage-operators
groupadd storage-leads

# named human accounts — NO shared logins, NO shared keys
useradd -m -G storage-operators alice
useradd -m -G storage-operators,storage-leads bob   # bob is also a lead

# each person installs their OWN ssh public key
mkdir -p /home/alice/.ssh && cp alice.pub /home/alice/.ssh/authorized_keys
chown -R alice:alice /home/alice/.ssh; chmod 700 /home/alice/.ssh

Project ownership & permissions

The project is owned by the service account, group-readable by operators, and not writable by anyone but the deploy path:

mgmt noderoot
chown -R svc-ansible:storage-operators /etc/ansible/Ansible_Simulator_Lab
# operators: read + traverse + execute; NOT write
chmod -R 750 /etc/ansible/Ansible_Simulator_Lab
# vault password readable only by the service account
chown svc-ansible:svc-ansible /etc/ansible/Ansible_Simulator_Lab/.vault_pass
chmod 600 /etc/ansible/Ansible_Simulator_Lab/.vault_pass
Deploys pull as the service account
Only the service account (or a lead via it) runs git pull to update the box from main. Operators never write to the directory — they only execute through the scoped sudo rule in the next section. This keeps the box a read-only target even for people who can run automation on it.

07 Scoped sudo rules

Operators must run specific automation without gaining a root shell or the ability to edit. sudo grants named commands as the service account — nothing more. Edit via visudo -f so syntax errors can't lock you out:

visudo -f /etc/sudoers.d/storageroot
# Operators may run the export wrapper and lab playbooks AS svc-ansible.
# They may NOT get a shell, edit files, or run arbitrary ansible.
Cmnd_Alias LAB_RUN = \
  /bin/bash /etc/ansible/Ansible_Simulator_Lab/scripts/run-facts-export.sh, \
  /bin/bash /etc/ansible/Ansible_Simulator_Lab/scripts/run-facts-export-prod.sh, \
  /usr/local/bin/ansible-playbook /etc/ansible/Ansible_Simulator_Lab/playbooks/0[0-9]-*.yml

%storage-operators ALL=(svc-ansible) NOPASSWD: LAB_RUN

# Leads may also pull/deploy and re-baseline.
Cmnd_Alias LAB_DEPLOY = \
  /usr/bin/git -C /etc/ansible/Ansible_Simulator_Lab pull, \
  /root/lab-verify.sh baseline

%storage-leads ALL=(svc-ansible) NOPASSWD: LAB_RUN, LAB_DEPLOY

An operator then runs the export attributably, as the service account, without ever touching the files:

alice@mgmtoperator
sudo -u svc-ansible /bin/bash \
  /etc/ansible/Ansible_Simulator_Lab/scripts/run-facts-export.sh
Pitfalls that turn a scoped rule into root
Never grant sudo to a command that can spawn a shell or read arbitrary files — vi, less, find -exec, awk, or a bare ansible with -m shell all become root shells. Scope to the exact wrapper scripts and the numbered playbooks only. Wildcards like playbooks/*.yml are acceptable; a wildcard that lets the user supply -e arbitrary modules is not. Audit the rule with sudo -l -U alice.

08 Attribution & audit

Authorization is half the goal; the other half is proving who did what. Every layer contributes a piece of the audit trail.

ActionRecorded byWhere to look
Code changeSigned Git commitgit log --show-signature
Change approvalPR review recordGitHub PR history
Deploy (pull) to boxsudo logjournalctl /usr/bin/sudo
Playbook runsudo log + Ansible/var/log/secure, ansible logs
File tamperingChecksum baseline/root/lab-verify.sh check

The shared-root anti-pattern

The single most important attribution rule: no shared root login, no shared SSH key. A shared account makes "who did this?" unanswerable — every action attributes to "root", i.e. to nobody. Disable direct root SSH and require named accounts:

/etc/ssh/sshd_configroot
PermitRootLogin no
PasswordAuthentication no
AuthenticationMethods publickey

Tamper baseline (catches what bypasses the process)

Even with all controls, a checksum baseline proves whether on-box files match the approved state — catching anything that bypassed Git entirely:

mgmt noderoot
# after each deploy, re-baseline; check daily via cron
/root/lab-verify.sh baseline
( crontab -l; echo "0 6 * * * /root/lab-verify.sh check | logger -t lab-verify" ) | crontab -

09 End-to-end deployment flow

The whole model in motion — a change from idea to running on production, with authorization and attribution at every step:

1

AUTHOR

An engineer branches, edits a playbook, signs the commit, pushes, and opens a pull request. They cannot push to main directly — branch protection blocks it.

2

REVIEW

CI runs lint-check.sh on the PR (required status check). A storage-lead reviews the diff; CODEOWNERS requires their approval for /playbooks/. The author cannot approve their own PR.

3

MERGE

On approval + green CI, a lead merges to main. The signed-commit requirement means the history is cryptographically attributable.

4

DEPLOY

On the mgmt node, a lead pulls the reviewed main as the service account (sudo -u svc-ansible git -C ... pull), then re-baselines the checksum manifest. The box now matches approved state. Nobody edited anything on the box.

5

RUN

An operator executes the playbook through the scoped sudo rule. The run is logged against their name. They could not have changed what the playbook does.

No single point of unchecked power
Notice no one person can both change automation and run it on production without review. The author can't merge or deploy; the operator can't edit; the lead's merges are signed and logged. That separation is the entire point — it makes both accidents and abuse require collusion or leave a trail.

10 Implementation checklist

Git layer

  • Repo private; create teams storage-engineers / -leads / -operators / -auditors with Write / Maintain / Read / Read.
  • Branch protection on main: require PR, require approvals, require Code Owner review, require signed commits, require status checks, no admin bypass, restrict merge to leads.
  • Add .github/CODEOWNERS mapping paths to teams.
  • Add a GitHub Actions workflow running scripts/lint-check.sh; mark it a required check.

OS layer

  • Create svc-ansible service account; create role groups; create named human accounts in the right groups.
  • Each person installs their own SSH key; disable PermitRootLogin and password auth.
  • chown svc-ansible:storage-operators the project; chmod 750; vault pass 600 to the service account.
  • Author /etc/sudoers.d/storage via visudo -f with scoped Cmnd_Alias rules; verify with sudo -l -U <user>.

Attribution

  • No shared root / shared keys — named accounts only.
  • Enable signed commits; keep PR history.
  • Install lab-verify.sh; baseline after each deploy; daily check via cron to syslog.
  • Confirm sudo logging reaches /var/log/secure / journald.
Scaling down without losing the shape
A smaller team can collapse roles (one person may be engineer + lead) while keeping the mechanisms: still use PRs and branch protection even if you sometimes approve your own emergency change, still use named accounts and scoped sudo. The structure costs little once set up and builds the audit trail and habits that a growing team will need — far easier than retrofitting separation after an incident.

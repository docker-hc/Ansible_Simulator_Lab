01 Why ESXi, not a file share

The instinct — "move the VM files to a company share" — mixes up two different things. A file share (SMB/NFS) is storage; an ESXi host is a hypervisor. You can park powered-off VM files on a share, but running a VM whose virtual disk lives on a network share is slow and corruption-prone: every disk I/O crosses the network, and a brief disconnect mid-write can wreck the disk. So the share is fine for staging and backups, but the lab should run on ESXi.

This also fixes the travel problem — which the share does not
The "can't use it when travelling" issue is about the bridged 192.168.2.x network, not about where the files live. Moving files to a share changes nothing there. Running the lab on an always-on ESXi host and reaching it over WireGuard (Document 6) is what actually solves travel: you don't carry the lab, you tunnel to it. ESXi delivers off-the-laptop, always-on, and team-accessible in one move.

Recognise what this migration really is: the lab stops being "a thing on a laptop" and becomes a shared service on company infrastructure — the production posture of Documents 4 and 7.

02 Prerequisites & what to request

Before touching a VM, confirm two non-technical things and gather what you will need from whoever runs the platform.

Confirm the CPU constraint is gone

The lab runs Rocky 9 (not RHEL 10) only because the laptop CPU is x86-64-v2. A server-grade ESXi host is almost certainly x86-64-v3+, so that constraint likely disappears — you could even run RHEL 10 on rebuilt VMs later. Confirm the host's CPU generation so you are not surprised either way.

What to request from the platform team

ResourceFor the lab
Datastore space~200–300 GB for the 5 VMs (mgmt 16 GB RAM disk + 4 sims + 2 nodes)
vCPU / RAMmgmt 4 vCPU / 16 GB; each sim 2 vCPU / 8 GB; nodes 1 vCPU / 2 GB
Port group / VLANone network the VMs share (replaces the bridged + internal nets)

Upload methodvSphere web client access, or OVF Tool + host credentials
This is a request, not a self-service action
Datastore space, a port group, and IPs are granted by whoever runs the ESXi platform. Bring the resource list above. Also confirm whether you may upload OVAs directly or must hand them to an admin to import.

03 Prepare the VMs (laptop side)

A little cleanup before export makes the import far smoother.

1

POWER DOWN CLEANLY

Shut each guest down from inside (shutdown -h now), not a hard power-off, so filesystems are consistent in the exported image.

2

REMOVE VBOX GUEST ADDITIONS

They are VirtualBox-specific and conflict with VMware Tools later. On each guest before shutdown:

each guestroot
/opt/VBoxGuestAdditions-*/uninstall.sh 2>/dev/null || true
dnf remove -y VirtualBox-guest-additions 2>/dev/null || true
3

NOTE THE CURRENT MACS & IPS

You will re-pin these after import. Record, per VM, the bridged IP, internal IP, and the mgmt node's MAC (the KPN port-forward and DHCP reservation key off it):

each guestroot
ip -br addr ; ip link show | grep ether
4

DETACH SHARED FOLDERS / ISOs

Remove the VirtualBox shared folder (/mnt/vm_share) mounts and any attached ISOs — they will not exist on ESXi and cause boot delays. Comment their lines out of /etc/fstab.

04 Export to OVA

OVA is a single portable file bundling the VM config and disks, understood by both VirtualBox and VMware. Export each powered-off VM. Use OVF 2.0 for best VMware compatibility:

laptop — per VMVBoxManage
VBoxManage export "Rocky9-Ansible-Mgmt" \
  -o Rocky9-Ansible-Mgmt.ova --ovf20

# repeat for each:
VBoxManage export "rocky9-sim-810294" -o sim-810294.ova --ovf20
VBoxManage export "rocky9-sim-840006" -o sim-840006.ova --ovf20
# ...840006 / 845665 / 845666, plus the two RHEL nodes
The file share earns its keep here
Stage the .ova files on the company file share — that is the right use of it. It gives the ESXi host a place to pull from, and leaves you a portable backup of each VM. Keep these OVAs even after a successful migration; they are a clean rebuild point.

Export is slow (each disk is compressed into the OVA) — budget time and disk space for roughly the size of the used data across all VMs.

05 Import into ESXi

Two ways, depending on the access you were granted.

A — vSphere / ESXi web client (GUI)

  1. Log into the ESXi host or vCenter web client.
  2. Create / Register VM → Deploy a virtual machine from an OVF or OVA file.
  3. Upload the .ova (or point at it on the datastore/share), pick the datastore, pick the target port group, and finish.
  4. The disk converts (VDI → VMDK) automatically during deploy.

B — VMware OVF Tool (command line)

workstation with ovftool
ovftool \
  --datastore=datastore1 \
  --network="Lab-PortGroup" \
  --name="Rocky9-Ansible-Mgmt" \
  Rocky9-Ansible-Mgmt.ova \
  "vi://user@esxi-host.company.local/"
If import rejects the OVA
VirtualBox OVAs occasionally trip VMware's stricter OVF validation (a SHA-manifest or hardware-version quirk). Two fixes: re-export with --ovf20 (done above), or pass ovftool --lax to relax validation. If a specific virtual hardware item is rejected, importing the .ovf+.vmdk pair (export without packaging into a single OVA) often sidesteps it.

06 Re-map networking

This is the biggest conceptual change. On the laptop you had a bridged adapter (192.168.2.x) and an internal adapter (192.168.56.x). On ESXi those become port groups, and the company network is different from your home 192.168.2.x.

Two viable models

ModelHowWhen
Keep lab subnets, isolatedCreate an ESXi internal-only port group (no uplink) carrying 192.168.2.x + 192.168.56.x exactly as today; only the mgmt node also gets a company-network NIC for accessLeast change — HORCM, SAM4H, all configs keep their IPs; recommended
Re-IP onto company netPut VMs directly on a company port group with company IPsOnly if policy requires it — means re-IPing every config
Recommended: isolated lab network + dual-homed mgmt node
Create an internal vSwitch/port group with no physical uplink and keep the lab on 192.168.2.0/24 + 192.168.56.0/24 untouched — every array IP, HORCM_CMD line, SAM4H registration, and the facts vault stay valid with zero edits. Give the mgmt node a second NIC on a company port group (or keep WireGuard as the only entry). The mgmt node remains the single gateway, exactly as in the remote-access design. This is by far the least disruptive path.

In the VM settings after import, set each NIC's adapter type to VMXNET3 (best ESXi performance) and attach it to the correct port group. The guest sees a new NIC name (e.g. ens192 instead of enp0s3) — you will fix that in §08.

07 Guest Additions → VMware Tools

With Guest Additions already removed (§03), install open-vm-tools on each guest after first boot on ESXi — it provides the guest/host integration VMware expects (clean shutdown, time sync, IP reporting):

each guest on ESXiroot
dnf install -y open-vm-tools
systemctl enable --now vmtoolsd

On the sim VMs, integsim and its nginx dependency are unaffected by the hypervisor change — libxcrypt-compat and the rest carry over in the disk image. Only the kernel/hypervisor integration layer changes.

08 Re-pin MAC-dependent pieces

Import gives each VM a new MAC address, and the guest sees a new NIC name. Several things keyed off the old values must be re-pinned, or the lab comes up with the wrong addresses.

1

FIX THE NIC NAME / IP BINDING

NetworkManager bound the static IP to the old interface (enp0s3). On ESXi the NIC is typically ens192. Re-create the connection on the new interface:

each guestroot
nmcli con show                       # find the new device name
nmcli con add type ethernet ifname ens192 con-name lab \
  ipv4.method manual ipv4.addresses 192.168.2.91/24 \
  ipv4.gateway 192.168.2.254 ipv4.dns 8.8.8.8
nmcli con up lab

Use each VM's own recorded IP from §03. The sims keep .90/.92/.93/.94; the mgmt node keeps .91.

2

RE-POINT THE PORT-FORWARD / DHCP RESERVATION

If you kept WireGuard on the mgmt node, the inbound port-forward (UDP 51822) and any DHCP reservation were tied to the old MAC. On the new network's router/firewall, update the forward to the mgmt node's new IP, and reserve the new MAC. If the lab is now behind the company network, this may instead be a company firewall rule or VPN — coordinate with the platform team.

3

WIREGUARD & DUCKDNS

The WireGuard config (keys, peers, 10.99.99.x) is in the disk image and survives. What changes is the endpoint: the lab now lives behind the company's public IP, not your home KPN line. Update DuckDNS to the new public IP (or, if the company gives the host a static public IP, point the client Endpoint straight at it and retire DuckDNS). Re-test from outside per Document 6 §11.

4

HORCM IS UNAFFECTED — IF YOU KEPT THE SUBNETS

Because HORCM_CMD uses the array IPCMD addresses (192.168.2.90 etc.), keeping the isolated lab subnet (§06 recommended model) means every HORCM config, SAM4H registration, and the facts vault stay valid with no edits. This is the single biggest reason to keep the lab subnets rather than re-IP.

09 Bring-up & verify

Boot in the same dependency order the lab always used: sims first (so their REST surfaces are live), then the mgmt node (which starts HORCM against them).

verification from the mgmt noderoot
# network identity correct?
ip -br addr | grep 192.168.2.91
# sims reachable on REST?
for ip in 90 92 93 94; do curl -sk -o /dev/null -w "%{http_code}\n" https://192.168.2.$ip; done
# HORCM sees the arrays?
for i in 1001 1004 1005 1006; do raidqry -l -IH${i} | grep -vE '^No|^$|^Group' | head -1; done
# full pipeline still works?
bash scripts/run-facts-export.sh
# tamper baseline will differ (new MACs/NIC names) — re-baseline once verified:
bash scripts/harden-lab.sh --lock
Expect the tamper baseline to flag changes
The NIC reconfiguration legitimately changes files. After confirming the lab is healthy, run harden-lab.sh --lock to re-baseline so the post-migration state becomes the new known-good. This is the intended use of the re-baseline step.

10 After migration

What got better

  • Always-on — the lab runs on the host regardless of your laptop, so travel access (via WireGuard) is reliable.
  • Off your laptop — disk space and resources freed; the laptop is now just a client.
  • Team-ready — shared infrastructure makes the access-control model of Document 7 (named accounts, groups, scoped sudo) the natural way to govern it.
  • Snapshots are first-class — ESXi/vCenter snapshots and (if available) backup tooling replace the fragile shared-base-disk VirtualBox snapshots.

Cleanup & records

  • Keep the OVAs on the share as a rebuild point until the ESXi VMs have run cleanly for a while.
  • Take a fresh ESXi snapshot of the mgmt node once verified (name e.g. esxi-vspb26-migrated-2026).
  • Commit any config changes (NIC names, endpoint) to the repo; re-run harden-lab.sh --lock to re-baseline.
  • Update the WireGuard/DuckDNS notes in Document 6 to reflect the new endpoint.
Relationship to the other documents
This migration turns the lab into the shared service that Documents 4 (production export), 6 (remote access), and 7 (access control) assume. Once on ESXi with the isolated lab subnet preserved, every prior document applies unchanged — only the hosting layer beneath them moved.
Reconsider the OS now the CPU constraint is gone
On server-grade ESXi hardware the x86-64-v2 limit that forced Rocky 9 likely no longer applies. You do not have to change anything — the migrated Rocky 9 VMs run fine — but if you ever rebuild, RHEL 10 / newer SVOS support becomes an option worth weighing (see Document 5 on model/microcode currency).

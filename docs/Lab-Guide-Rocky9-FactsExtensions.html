01 What this adds

The base export (Document 4) gathers six fact types. This extension adds three more to the same pipeline: licenses, host mode options, and journals — each surfacing in both the Excel workbook and the CSV set as new tabs/files.

Fact typeSourceModule / toolPer-array count (B26 sim)
Licensesraidcomgather_licenses.py24 products
Host mode optionsRESThv_supported_host_mode_facts37 options
JournalsRESThv_journal_facts0 (none configured)
Why two different mechanisms
Host mode options and journals come from Ansible REST fact modules. Licenses are not exposed by any VSP Ansible module (only SDS Block has one), so licenses are read via raidcom get license, mirroring the existing HBA-WWN collector. One pipeline, two gather mechanisms.

02 Licenses via raidcom

Because no VSP license fact module exists, gather_licenses.py runs raidcom get license per HORCM instance. It mirrors gather_hba_wwn.py: takes the same serial:instance map, logs in itself with the vault credentials, parses, logs out.

The playbook task

playbooks/08-export-facts.ymlafter the HBA WWN task
- name: Gather licenses via raidcom
  ansible.builtin.command:
    argv:
      - python3.11
      - "{{ playbook_dir }}/../scripts/gather_licenses.py"
      - "--map"
      - "{{ hba_map }}"          # reuses the WWN map
      - "--user"
      - "{{ vault_raidcom_user }}"
      - "--password"
      - "{{ vault_raidcom_password }}"
      - "--out"
      - "{{ raw_dir }}/licenses.json"
  changed_when: false

The output format

Real B26 raidcom get license output has the licence name as a trailing quoted field (may contain spaces, e.g. "global-active device"). The parser keys off the header and extracts the quoted name reliably. Each row gets the raw columns plus a derived installed boolean (from STS == INS). The diff keys on PRO_ID (product id).

Prerequisite: HORCM up + login
The license gather needs a running HORCM instance and an authenticated session — the production wrapper does horcmstart (with a teardown trap), and the script does its own raidcom -login. Without HORCM attached you get raidcom: [EX_ATTHOR] Can't be attached to HORC manager (see §06).

03 Host mode options

Two distinct things, both worth having: the supported HMO catalog (the array's full option list) from hv_supported_host_mode_facts, and the per-host-group assignments (already inside host_groups.json as hostMode / hostModeOptions).

playbooks/08-export-facts.ymlREST, after host groups
- name: Gather supported host mode options
  hitachivantara.vspone_block.vsp.hv_supported_host_mode_facts:
    connection_info:
      address: "{{ item.controller_ip_0 }}"
      username: "{{ vault_raidcom_user }}"
      password: "{{ vault_raidcom_password }}"
  register: hmo_facts
  loop: "{{ vault_arrays }}"
  loop_control:
    label: "{{ item.serial }}"
The catalog is nested
The module returns { host_modes: { host_mode_options: [...] } } — the options list is one level deeper than a normal fact payload. The loader must unwrap host_modes.host_mode_options or it stores a dict instead of the list (37 options collapsed to a useless single entry). Diff key: host_mode_option_id. The B26 catalog is 37 options, identical across same-model arrays.

04 Journals

Journal volumes (Universal Replicator async replication) come from hv_journal_facts. The task mirrors the other REST gathers. On the static sims there are none configured, so the module returns { journal_volume: null }.

Empty is correct, not a bug
journal_volume: null means no journals exist — expected on the sims. The loader must turn null into an empty list so it renders as a clean empty tab rather than crashing or emitting a stray row. On a real array with UR configured, journals populate normally; verify the diff key (journalId is a reasonable guess) against real output then, since the sims can't confirm it.

Use the hv_journal_facts module — not the deprecated hv_journal_volume_facts, which is removed in collection 5.0.0.

05 Two loaders, two fixes

The critical structural lesson: facts_to_xlsx.py and facts_to_csv.py each have their own independent load_raw. Every loader change must be applied to both, or one output silently diverges from the other.

Register the new types (both scripts)

both scriptspython
FACT_TYPES = ["system", "parity_groups", "ports", "pools", "ldevs",
              "host_groups", "host_mode_options", "journals", "licenses"]

The loader normalisation (both scripts)

load_raw(), per fact typepython
serial = str(item.get("item", {}).get("serial") or item.get("serial", "unknown"))
payload = extract_payload(item.get("ansible_facts", {}))
if ft == "host_mode_options" and isinstance(payload, dict):
    payload = payload.get("host_mode_options", [])   # unwrap nested
if ft == "journals":
    payload = payload or []                          # null -> []
if payload is None:
    payload = []

KEY_FIELDS (xlsx diff)

"host_mode_options": ["host_mode_option_id"],   # confirmed
"journals":          ["journalId"],             # guess (no journals on sims)
"licenses":          ["PRO_ID"],               # confirmed

The meta-lesson
Two scripts with independent load_raw functions means every data-shape fix is a two-place edit. The long-term fix is to factor the shared loader into one module both import — until then, treat "fixed in xlsx" as only half done.

07 Hardening: harden-lab.sh

One command applies baseline protection: tamper-detection, read-only locking, secret guards, and an SSH audit. It is idempotent, reversible, and reports rather than silently locking you out.

ModeDoes
(none)apply: install verify script, baseline, daily cron, lock dirs, gitignore guards, SSH audit
--statusdashboard: lock state, baseline age, tamper result, cron presence
--checkrun the tamper check (what changed since baseline)
--unlockmake code writable to edit
--lockre-lock + refresh baseline
Read permission BITS, not -w (the root trap)
Lock-state detection must read stat -c '%A' bits, not [ -w ] — root bypasses the write bit, so -w reports a locked dir as writable. This subtlety is why --status uses stat.
Prevent / detect / recover
Read-only locking prevents accidental edits (a deliberate-change speed bump, not absolute — root can override). The checksum baseline detects any change, even one that bypasses Git. Git recovers. The three layers stack; no single one is the whole defence. Relationship to Document 7: that doc covers team RBAC; this script is the single-machine implementation.

08 Edit-while-locked workflow

Once hardening is applied, the directories are read-only, so editing follows a rhythm that keeps the baseline honest:

1

UNLOCK

mgmt noderoot
bash scripts/harden-lab.sh --unlock
2

EDIT + COMMIT

Make changes, run the lint check, commit and push. Watch for the gotchas in §06 — strip trailing whitespace, keep __pycache__ out of Git.

3

RE-LOCK + RE-BASELINE

mgmt noderoot
bash scripts/harden-lab.sh --lock      # re-locks AND refreshes baseline
bash scripts/harden-lab.sh --status    # confirm clean

Re-locking refreshes the baseline so your committed change becomes the new known-good — skip it and the daily check flags your own edit.

Checkpoint order
The full session checkpoint: verify export → --unlock → gitignore secret guards + git status review → lint → commit → push → --lock → shutdown → VM snapshot. Hardening runs effectively last because it locks the very directories Git tracks.

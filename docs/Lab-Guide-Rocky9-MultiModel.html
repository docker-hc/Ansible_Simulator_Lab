01 Summary

Three questions were raised: does the toolchain support the VSP One 360 and B85; are different YAML files used per model; and are they available. Short answers:

  • B26 — supported and proven. It is explicitly listed in the 4.8.1 hardware table.
  • B85 — the B85 is the VSP One Block High End product, and the High End tier is listed in the 4.8.1 table, so it is expected to work — but the B85 is a different, multi-controller architecture released after 4.8.1's docs, so its topology-aware facts should be verified live before relying on them.
  • "VSP One 360" — not a model name in the current portfolio; the high-end tier is branded VSP One Block High End. If "360" is an internal/reseller label, it maps to that same High End row.
  • Per-model YAML — No. One playbook and one script set cover every model. There is nothing per-model to download or maintain.
  • Collection version — 4.8.1 is the current published release; nothing newer to upgrade to right now.
The one-line takeaway
The facts-export toolchain is model-agnostic by design. A B26, a B85, and a High End array are just separate entries in vault_arrays. The only open item is verifying the B85's multi-controller topology facts against a live unit.

The B85 starts as an 18 RU appliance and scales to 50 RU, in 2 / 4 / 6 node-pair configurations — each node has two controllers. The 24–28 models are conventional dual-controller systems. That architectural difference is the crux of the B85 caveat in §06.

03 Support matrix

The toolchain uses only the vsp namespace hv_*_facts modules. These are model-agnostic across the whole VSP block family the collection targets (VSP One Block, VSP 5000, VSP E, VSP F, VSP G).

Fact moduleB26B85 / High EndNotes
hv_storagesystem_factsYesVerifyIdentity, microcode, capacity, efficiency
hv_paritygroup_factsYesVerifyTopology-aware — check on multi-controller

Yes = listed/proven. Verify = expected to work; confirm against the live B85 because of the multi-controller topology. Expected = logical facts not tied to controller layout.

04 Per-model YAML?

No — and this is the key efficiency of the design.

One playbook, all models

08-export-facts.yml loops vault_arrays and calls the same six fact modules for every entry, regardless of model. A mixed fleet — B26, B85, High End — lives in one inventory and runs through one playbook. There is no "B85 module" versus a "B26 module"; the collection ships one set of vsp.hv_* modules that span the family.

group_vars/vault.yml — a mixed fleetencrypted
vault_arrays:
  - serial: 350001
    model: "VSP One Block 26"
    controller_ip_0: 10.20.30.41
    horcm_instance: 0
  - serial: 490001
    model: "VSP One Block 85"       # same structure
    controller_ip_0: 10.20.30.51
    horcm_instance: 1

Are they available?

Every module the toolchain needs is already present in 4.8.1. There is no per-model YAML to fetch. The vendor vsp_direct/ example playbooks are likewise generic across the family.

What scales when you add a model
Adding any array — any model — is one block in vault_arrays plus its HORCM config file (for the WWN-login gather). The playbook, the workbook builder, the CSV builder, and the diff need zero changes.

06 The B85 caveat

The reason B85 is "verify" rather than a flat "yes" is architecture, not module naming.

  • The B85 is the VSP One Block High End product, and High End is a listed row in the 4.8.1 hardware table — so support is expected.
  • But the B85 is a multi-controller, node-pair system (2/4/6 node-pairs, two controllers each), unlike the dual-controller 24–28. It also launched after the 4.8.1 documentation was written.
  • The facts most sensitive to that difference are the topology-aware ones — ports and parity groups — where a multi-controller layout has far more to enumerate. Logical facts (system, pools, LDEVs, host groups) are not tied to controller count and should behave normally.
Don't trust the table alone for a new architecture
A row in a hardware table is necessary but not sufficient evidence for a brand-new multi-controller platform. The five-minute, read-only live check in §07 is how you confirm it rather than assume it.

07 Verifying a live array

A read-only, non-disruptive check. If all three return complete data, the existing toolchain works on the B85 unchanged.

1

IDENTITY FIRST

collectorroot
ansible-playbook playbooks/vsp_direct/storagesystem_facts.yml \
  -e "storage_address=<b85-ip> \
      vault_storage_username=<user> vault_storage_secret=<pw>"

Expect: serial, model, microcode, total/free capacity, efficiency. If clean, the logical layer is fine.

2

THEN THE TOPOLOGY-AWARE FACTS

collectorroot
ansible-playbook playbooks/vsp_direct/paritygroup_facts.yml -e "..."
ansible-playbook playbooks/vsp_direct/storage_port_facts.yml -e "..."

These are the multi-controller-sensitive ones. Complete output across all controllers/node-pairs = the B85 is fully covered.

3

INTERPRET

  • All three complete → run the full run-facts-export against the B85; no changes needed.
  • Partial / empty topology facts → the toolchain still reports what it gets; treat ports/parity as incomplete and re-check after the next collection upgrade.
  • Diff shows all-added/all-removed for a fact type → identity key differs on this microcode; adjust KEY_FIELDS (Troubleshooting F-2).
Confirm microcode meets the minimum
Below-minimum firmware causes partial facts regardless of collection version. Minimums: VSP One Block 26 → A3-05-21-40/00 / SVOS 10.5.2; High End / B85 → A0-05-41-00_01 / SVOS 10.5.3. Check the running version on each target before concluding a module is unsupported.

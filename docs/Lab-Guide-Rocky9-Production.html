01 Lab vs production

The reporting layer is environment-agnostic and moves across unchanged. What differs is the connection layer beneath it: how raidcom reaches the array, which account it uses, and how cautious you must be. The decoupled design (gather → JSON → workbook) is what makes this a configuration change rather than a rewrite.

LAB (simulator)

  • integsim IPCMD command device \\.\IPCMD-ip-31001
  • SAM4H drives CCI reload; auto-assigns HORCM instances
  • maintenance OS-auth account
  • Boot-time auto-start (cron @reboot)
  • Mutating the array is harmless
  • Tiny datasets; runs in seconds

PRODUCTION (live VSP)

  • Real command device LDEV, /dev/mapper/... path
  • No SAM4H; REST API direct to the controller
  • Dedicated admin/service account, secret in Vault
  • On-demand only; HORCM up/down per run
  • Read-only command device — mutations must be impossible
  • Thousands of LDEVs; first run takes minutes
What carries over untouched
08-export-facts.yml, facts_to_xlsx.py (Summary, Changes, per-array, per-fact-type, All-HBA-WWNs, empty-HG flag), facts_to_csv.py, the diff engine, and the run-over-run highlighting. Only the connection layer changes.

02 The collector host

A single Linux host (RHEL/Rocky 8.9+ or equivalent) runs everything. It needs the automation stack, the collection, CCI, and routes to each array's REST endpoint and command device.

collector — one-time setuproot
python3.11 -m pip install ansible-core==2.16.18 openpyxl
ansible-galaxy collection install hitachivantara.vspone_block:==4.8.1
# CCI from the RMHORC bundle (provides raidcom, horcmstart.sh, raidqry)
# place the repo, e.g. /opt/vsp-reporting
git clone git@github.com:<org>/vsp-reporting.git /opt/vsp-reporting
  • Network: TCP 443 from the collector to each array's REST controller address.
  • SAN/iSCSI: a path to each array carrying the presented command device LDEV.
  • No SAM4H, no podman — those were lab-only.

Keep the same project layout as the lab so the scripts find their relative paths. exports/ stays git-ignored; the workbook and CSVs are regenerable output.

03 Command device setup

This is the one piece of real plumbing. The WWN-login gather needs raidcom, and raidcom on a live array needs a genuine command device — a small LDEV presented to the collector and flagged as a command device. The storage admin does the array side once; you identify and wire it on the collector.

1

ARRAY SIDE (storage admin, once per array)

Create or designate a small LDEV, set it as a command device with user authentication ON and read-only / device-protect ON, and present it to the collector's HBA/iSCSI initiator.

2

COLLECTOR SIDE — identify the device

collectorroot
# rescan after the LUN is presented
rescan-scsi-bus.sh || echo 1 > /sys/class/scsi_host/host0/scan
lsscsi | grep -i hitachi
ls -l /dev/disk/by-id/        # find a stable path for the cmd device
# with multipath (FC):
multipath -ll
3

USE A STABLE PATH

Reference the command device by a path that survives reboots — a /dev/mapper/ multipath name or a /dev/disk/by-id/ link — never a bare /dev/sdb, which can renumber.

Read-only + user-auth is mandatory in production
A read-only command device makes it impossible for any raidcom verb — or a fat-fingered command — to alter array configuration. User authentication ties command-device access to the service account. Both were optional in the lab and are non-negotiable against live hardware. The facts export only ever issues raidcom get ..., so read-only costs nothing.

04 Authentication

You are using an existing admin account. That works, but treat it with production discipline: the secret lives only in Ansible Vault, never on the command line or in a playbook, and the same credential is reused for both REST (module connection_info) and the command-device user-auth.

ansible-vault edit group_vars/vault.ymlencrypted
vault_raidcom_user: "svc_storage_admin"
vault_raidcom_password: "<secret>"
Prefer least privilege where you can
A read-only / monitoring role is safer than a full admin account for a reporting job, and pairs naturally with a read-only command device. If account creation isn't an option right now, the read-only command device still prevents config changes via CCI — the REST modules used here are all _facts (read) modules regardless.

05 Array inventory

Each live array is one entry in vault_arrays — the same structure the lab used, now pointing at production controller addresses and a real HORCM instance per array.

group_vars/vault.ymlencrypted
vault_arrays:
  - serial: 350001
    model: "VSP One B26"
    controller_ip_0: 10.20.30.41   # REST endpoint
    horcm_instance: 0              # matches /etc/horcm0.conf
  - serial: 350002
    model: "VSP One B26"
    controller_ip_0: 10.20.30.42
    horcm_instance: 1

The playbook and workbook builders loop this list with no code change. Adding an array is one block here plus its HORCM config file.

07 Production wrapper

The lab wrapper auto-started at boot and copied to a Windows share. The production variant is the opposite: it brings HORCM up only for the run, tears it down on exit (even on error, via trap), and writes outputs locally. Instance numbers are derived from the vault so there is one source of truth.

scripts/run-facts-export-prod.shbash
#!/bin/bash
# On-demand production facts export. Read-only against live arrays.
set -euo pipefail
cd "$(dirname "$0")/.."

# derive HORCM instances from the vault array list
INSTANCES=$(ansible localhost -m debug \
  -a "var=vault_arrays" -e @group_vars/vault.yml 2>/dev/null \
  | grep -oP '"horcm_instance":\s*\K[0-9]+' | sort -u | tr '\n' ' ')
[ -z "$INSTANCES" ] && { echo "no instances in vault"; exit 1; }

# bring HORCM up; guarantee shutdown on any exit
horcmstart.sh $INSTANCES
trap 'horcmshutdown.sh $INSTANCES >/dev/null 2>&1 || true' EXIT

# 1 - gather (REST facts + raidcom WWN logins)
ansible-playbook playbooks/08-export-facts.yml
# 2 - workbook with run-over-run diff
python3.11 scripts/facts_to_xlsx.py --raw exports/raw
# 3 - CSV mirror
python3.11 scripts/facts_to_csv.py --raw exports/raw --out exports/csv
# 4 - archive this run; keep last 60 for production history
STAMP=$(date +%Y-%m-%d_%H%M%S)
mkdir -p "exports/history/$STAMP"
cp -f exports/raw/*.json "exports/history/$STAMP/"
ls -1dt exports/history/*/ | tail -n +61 | xargs -r rm -rf

echo "Done: $(ls -1t exports/*.xlsx | head -1)"
Why the trap matters
trap '... ' EXIT runs the HORCM shutdown whether the playbook succeeds, fails, or is interrupted. Against production you never want HORCM left running attached to a live command device after an aborted job.

08 On-demand run

The whole operation is one command, run when you want a snapshot — before/after a change window, during an audit, or to feed a migration plan.

collectoroperator
cd /opt/vsp-reporting
bash scripts/run-facts-export-prod.sh

Diff against a fixed point

For change-window verification, capture a baseline before the change and diff the after-run against it:

collectoroperator
# before the change
bash scripts/run-facts-export-prod.sh
cp -r exports/raw exports/baseline_change123

# after the change — highlight exactly what moved
bash scripts/run-facts-export-prod.sh
python3.11 scripts/facts_to_xlsx.py --raw exports/raw \
       --prev exports/baseline_change123
This is where the diff earns its keep
On live arrays the Changes tab answers the real question: what changed since I last looked? A new LDEV, a host group that gained a WWN, a pool that grew, a port that went offline — each surfaces green/amber/red without reading thousands of rows by hand.

09 Scale & safety

Dataset size

Real arrays return far more than the simulators. The ldev fact in particular can run to thousands of rows. The workbook handles it, but the first run may take minutes and the per-array LDEV section gets long. If LDEV volume is unwieldy, add a flag to summarise (count + capacity rollup) instead of enumerating every LDEV on the per-array tabs, keeping the full list on the All-LDEVs tab and the CSV.

Diff keys on real microcode

The diff identity fields were validated against simulator output. Pools and host groups are the most likely to use a different key on production microcode. If a first run-over-run diff shows a whole fact type as all-added + all-removed (never changed), adjust KEY_FIELDS in facts_to_xlsx.py — see Troubleshooting F-2.

Safety posture

  • Read-only command device + _facts modules only — the job cannot mutate config by design.
  • HORCM up/down per run via the trap — nothing persists against the array between runs.
  • Secret in Vault only — never on the command line, never echoed.
  • Stable command-device path — by-id/mapper, so a reboot can't point HORCM at the wrong LUN.
  • Run in a maintenance/observation window if your change-control process requires it, even for read-only access.
The one rule that separates lab from production
In the lab, a wrong command harmed nothing. Against live hardware, the read-only user-authenticated command device is the guardrail that keeps a reporting job from ever becoming a change. Set it up once, verify it, and the rest of the toolchain is as safe as it was in the lab.

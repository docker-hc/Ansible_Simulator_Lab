Remote Access
WireGuard VPN to the lab

Reaching the full lab from any location — SSH to the management node and browser access to SAM4H, Cockpit, and every array UI — over a self-hosted WireGuard tunnel, while sidestepping the overlapping-subnet problem that breaks remote access to a 192.168.2.x network.

01 Topology

WireGuard runs on the management node, which becomes the single VPN gateway into the lab. A remote device tunnels in, and the mgmt node routes its traffic onto the whole 192.168.2.0/24 — so you get both levels of reach: SSH to operate the lab, and browser access to SAM4H, Cockpit, and each array's REST UI. Your home router forwards one UDP port to the mgmt node; nothing else is exposed.

Why the mgmt node is the gateway
It already reaches everything — all four array REST surfaces, SAM4H, HORCM, the sim VMs. "Remote access to the lab" therefore reduces to "reach the mgmt node, then let it route." One MASQUERADE rule on the mgmt node gives full-subnet reach without adding a single route on the arrays or the router.

02 The subnet-conflict problem

This is the issue worth understanding before any config. 192.168.2.0/24 is one of the most common default home/office ranges. If you connect from a location that also uses 192.168.2.x, your device cannot tell whether 192.168.2.91 means "here" or "across the tunnel" — routing breaks. This is the classic overlapping-subnet conflict.

The fix used here: put the tunnel network on a deliberately exotic range — 10.99.99.0/24 — that will not collide with a typical local LAN. You then reach lab devices either by their lab IPs (when the local network is not 192.168.2.x) or, in the rare collision case, fall back to operating purely over SSH to the mgmt node's tunnel address 10.99.99.1.

The permanent fix, if you ever hit a collision
Because you control everything, the bulletproof option is to renumber the lab off 192.168.2.x onto something rare (e.g. 10.42.7.0/24). More work — every VM, the HORCM configs, the vault, the startup script — but it removes collisions for good. Only worth doing if you actually travel to 192.168.2.x sites. If you renumber, the only WireGuard change is the client's AllowedIPs line.

Forward one UDP port to the mgmt node. Use a non-default port (not 51820) to cut down on automated scan noise.

04 Install & keys

mgmt noderoot
dnf install -y wireguard-tools
cd /etc/wireguard
umask 077

# server keypair
wg genkey | tee server.key | wg pubkey > server.pub
# one keypair per client device (laptop)
wg genkey | tee laptop.key | wg pubkey > laptop.pub

cat server.key server.pub laptop.key laptop.pub
Key hygiene
Keep umask 077 so keys are root-only. Generate a separate keypair per device — never reuse the laptop key on a phone. Private keys never leave the device they belong to; only the matching public key goes into the other end's config.

05 IP forwarding

The mgmt node must route packets from the tunnel into the lab subnet.

mgmt noderoot
cat > /etc/sysctl.d/99-wireguard.conf << 'EOF'
net.ipv4.ip_forward = 1
EOF
sysctl --system
sysctl net.ipv4.ip_forward     # confirm = 1

06 Server config

First confirm the bridged interface name (the one holding 192.168.2.91) — the MASQUERADE rule references it:

mgmt noderoot
ip -br addr | grep 192.168.2.91     # note iface: enp0s3 / eth0 / ...

Then write the interface config. Tunnel net 10.99.99.0/24; mgmt node is .1, laptop .2:

/etc/wireguard/wg0.confroot, chmod 600
[Interface]
Address = 10.99.99.1/24
ListenPort = 51822
PrivateKey = <CONTENTS_OF_server.key>

# NAT tunnel traffic onto the lab LAN so replies route back.
# enp0s3 = bridged 192.168.2.x interface — adjust to yours.
PostUp   = iptables -t nat -A POSTROUTING -s 10.99.99.0/24 -o enp0s3 -j MASQUERADE
PostUp   = iptables -A FORWARD -i wg0 -j ACCEPT
PostDown = iptables -t nat -D POSTROUTING -s 10.99.99.0/24 -o enp0s3 -j MASQUERADE
PostDown = iptables -D FORWARD -i wg0 -j ACCEPT

[Peer]
# laptop
PublicKey = <CONTENTS_OF_laptop.pub>
AllowedIPs = 10.99.99.2/32
mgmt noderoot
chmod 600 /etc/wireguard/wg0.conf
systemctl enable --now wg-quick@wg0
wg show     # lists interface + laptop peer
Why MASQUERADE gives full-subnet reach for free
With the NAT rule, lab devices see tunnel traffic as coming from the mgmt node's own 192.168.2.91 — an address they already know how to answer. So SAM4H, Cockpit, and every array REST surface are reachable without adding routes on the arrays or the router. That is what turns "SSH to the mgmt node" into "reach the whole subnet".

07 Firewall

mgmt noderoot
firewall-cmd --permanent --add-port=51822/udp
firewall-cmd --permanent --add-masquerade
firewall-cmd --reload

08 Client config

Split tunnel — only lab traffic crosses the tunnel; normal internet stays direct. Endpoint is your home public IP or dyn-DNS name.

laptop — wg client configini
[Interface]
Address = 10.99.99.2/24
PrivateKey = <CONTENTS_OF_laptop.key>

[Peer]
PublicKey = <CONTENTS_OF_server.pub>
Endpoint = mylab.duckdns.org:51822
AllowedIPs = 10.99.99.0/24, 192.168.2.0/24
PersistentKeepalive = 25
  • AllowedIPs here is what delivers both reach levels: 192.168.2.0/24 routes the whole lab over the tunnel (browser to SAM4H / Cockpit / array UIs); 10.99.99.0/24 reaches the gateway itself.
  • PersistentKeepalive = 25 keeps the NAT mapping alive through the home router so the tunnel stays reachable.

Import on the laptop (WireGuard app on Windows/macOS, or wg-quick up on Linux) and connect.

09 Verify & add devices

laptop — once connectedoperator
ping 192.168.2.91                              # gateway over tunnel
ssh -i ~/.ssh/ansible root@192.168.2.91        # operate the lab
curl -sk https://192.168.2.90/ConfigurationManager/v1/objects/storages \
     -u maintenance:raid-maintenance           # array REST, end to end

Then in a browser: https://192.168.2.91:8080 (SAM4H), https://192.168.2.91:9090 (Cockpit), and the four array REST endpoints on .90 / .92 / .93 / .94.

Adding another device

Generate a fresh keypair, give it the next tunnel address, and append a peer block on the server — no restart-from-scratch needed:

mgmt noderoot
cd /etc/wireguard; umask 077
wg genkey | tee phone.key | wg pubkey > phone.pub
# append to wg0.conf:
#   [Peer]
#   PublicKey = <phone.pub>
#   AllowedIPs = 10.99.99.3/32
wg setconf wg0 <(wg-quick strip wg0)     # apply without dropping the tunnel

Onboarding a colleague

Each person needs the tunnel on their own machine — the lab lives on a private network, so https://192.168.2.91:8080 is unreachable without it. Give one person one keypair and one tunnel IP; never share a config between people, so any single person can be revoked by deleting just their peer block. The work splits cleanly between them and you.

WHAT THE COLLEAGUE DOES (on their machine)

  1. Install the WireGuard app (Windows/macOS/Linux/iOS/Android).
  2. Add an empty tunnel — it generates a keypair. They send only the public key to you (safe to share; the private key never leaves their device).
  3. You send back their tunnel Address and the server public key + endpoint; they paste the config below and save.
colleague's WireGuard clientini
[Interface]
PrivateKey = (their own, already generated — leave as-is)
Address = 10.99.99.5/24          # the IP YOU assign them

[Peer]
PublicKey = 3Gy9BeYq5oFGozEWjcGk4avhWkCKxhjcRRGpuYgsIwc=   # server public key
Endpoint = hitachivantara.duckdns.org:51822
AllowedIPs = 10.99.99.0/24, 192.168.2.0/24
PersistentKeepalive = 25

WHAT YOU DO (on the mgmt node)

Register their public key against the next free tunnel IP, then persist it so it survives a reboot:

mgmt noderoot
# add to the running tunnel (takes effect immediately)
wg set wg0 peer <COLLEAGUE_PUBLIC_KEY> allowed-ips 10.99.99.5/32

# persist in the config so it survives reboot / restart
cat >> /etc/wireguard/wg0.conf << 'EOF'

[Peer]
# colleague — jane
PublicKey = <COLLEAGUE_PUBLIC_KEY>
AllowedIPs = 10.99.99.5/32
EOF

wg show     # confirm the new peer is listed
Assign a unique IP per person
You (.1), laptop (.2), iPhone (.3) are taken — hand the next person 10.99.99.5, the one after 10.99.99.6, and so on. Each person's Address in their client and their allowed-ips on the server must match and be unique. Reusing an IP makes the two clients fight and neither works reliably.

TELL THEM TWO THINGS

  • The cert warning is normal. https://192.168.2.91:8080 uses a self-signed certificate, so the browser warns on first visit — click Advanced → Proceed anyway. Same for the Cockpit and array REST URLs.
  • Tunnel on only when away. If they are ever physically on the same 192.168.2.x network as the lab, the tunnel must be off (the hairpin problem in §11). From any other network, tunnel on. In practice a remote colleague just leaves it on.

REVOKING ACCESS

Remove the person's [Peer] block from /etc/wireguard/wg0.conf and reload — their config instantly stops working, no effect on anyone else:

mgmt noderoot
# edit out their [Peer] block, then:
wg setconf wg0 <(wg-quick strip wg0)     # apply without dropping the tunnel
# or, ad-hoc remove from the running tunnel immediately:
wg set wg0 peer <COLLEAGUE_PUBLIC_KEY> remove
When hand-managed peers stop scaling
A handful of people is fine to manage by hand this way. Past roughly five, the keypair-exchange and per-peer editing gets tedious — that is the point where a mesh VPN with a web admin (Tailscale, ZeroTier) starts to earn its place over hand-managed WireGuard. For a couple of colleagues, this runbook is all you need.

10 Real-world deploy: KPN + DuckDNS

The generic steps above assume a router you fully control and a static public IP. A real home ISP connection — here a KPN Box 12 with a dynamic IP — adds two moving parts: a dynamic-DNS name so the changing IP stays reachable, and the ISP router's particular port-forward behaviour. This is the configuration that actually got the lab online.

Dynamic DNS with DuckDNS

A home IP is rarely static. DuckDNS gives a free name that tracks it. Register at duckdns.org (sign in with any identity provider — it only confirms who you are, no repo access), add a subdomain (e.g. hitachivantara), and copy the account token. The client Endpoint then uses the name, not a number:

laptop / phone WireGuard clientini
Endpoint = hitachivantara.duckdns.org:51822

AUTO-UPDATER ON THE MGMT NODE

The name is only useful if something refreshes it when the IP rotates. The always-on mgmt node is the natural place for that — a tiny script on a 5-minute cron:

mgmt noderoot
mkdir -p /opt/duckdns
cat > /opt/duckdns/update.sh << 'EOF'
#!/bin/bash
curl -fsS "https://www.duckdns.org/update?domains=hitachivantara&token=__TOKEN__&ip=" \
  -o /var/log/duckdns.log
EOF
# insert the token without it showing on screen
read -rsp 'Paste DuckDNS token: ' T; echo
sed -i "s/__TOKEN__/$T/" /opt/duckdns/update.sh
chmod 700 /opt/duckdns/update.sh; unset T
/opt/duckdns/update.sh && cat /var/log/duckdns.log     # must print OK
# schedule exactly one entry
( crontab -l 2>/dev/null; echo "*/5 * * * * /opt/duckdns/update.sh >/dev/null 2>&1" ) | crontab -
The update URL is fragile to stray characters
The parameter is &ip= (empty = auto-detect the public IP). A single stray character on the end — &ip="=", ...22.64"4" — makes DuckDNS return KO instead of OK. If you get KO with a valid token, suspect the URL, not the token. Building it from $T / $DOMAIN variables avoids the trailing-character trap.

KPN Box 12 port-forward

On the KPN Box the feature is Netwerk → Poorten openzetten (port forwarding). The rule that works:

Field (NL)ValueNote
StatusONThe toggle must be green/on — a saved rule sits inactive until enabled
ProtocolUDPWireGuard is UDP only
Internet IP adres(empty)Source filter — leave blank to allow any source
Internet poort nummer51822External port
Doel IP-adres192.168.2.91The mgmt node
Doel poort nummer51822Internal port
Binding the rule to the device
KPN offers an Apparaat (device) dropdown. A VirtualBox VM (MAC prefix 08:00:27) bridged through the Windows host may not appear there the way a physical box does. The rule works bound by Doel IP-adres alone; if the form insists on a device, set the bridged adapter's Promiscuous Mode = Allow All in VirtualBox (VM powered off) so the VM is a first-class LAN device. A DHCP reservation for 192.168.2.91 keeps the target stable.

Confirm there is no CGNAT

Port-forwarding only works with a real public IP. Compare two numbers: what the world sees, and what the router's WAN shows.

any LAN machine
curl ifconfig.me              # e.g. 77.171.22.64
# compare to the KPN Box status page WAN IPv4

If they match, you have a routable public IP and forwarding works (this lab: they matched at 77.171.22.64). If the router shows a 100.64.x.x carrier address while the world sees something else, that is CGNAT — no IPv4 forward can work, and the fix is to use IPv6 instead (KPN assigns each device a routable IPv6 address, no forward needed).

11 Troubleshooting journey

Getting this online took a chain of dead-ends, each instructive. Recording them because the symptoms are misleading and the same traps recur on any home-ISP deployment. The order matters: each step ruled something out and pointed at the next.

The misleading symptoms

  • Tunnel "active" in the client app, but no ping, no access.
  • Activating the tunnel broke access to the local network and the router.
  • tcpdump on the server showed packets sometimes, silence other times — seemingly at random.

TRAP 1 — TESTING FROM INSIDE THE HOME LAN (hairpin)

The client `AllowedIPs` includes 192.168.2.0/24. When the test machine is on 192.168.2.x, activating the tunnel tells it to route its own LAN — including the router at .254 — through the tunnel, which it cannot deliver locally. Result: local access dies, and handshakes loop back through the router's NAT and fail. tcpdump showing a source of 192.168.2.100 is the tell. A tunnel whose AllowedIPs covers the local subnet simply cannot be tested from that subnet — it must be tested from genuinely outside (mobile data).

TRAP 2 — A SECOND, FULL-TUNNEL VPN

A commercial VPN tunnel was also configured on the laptop with AllowedIPs = 0.0.0.0/1, 128.0.0.0/1, ::/1, 8000::/1 — the "route everything" pattern. While active, it captured the lab handshake packets too, sending them out through the commercial provider instead of to the home IP. Two WireGuard tunnels with overlapping routes; the all-traffic one wins. Lesson: only one tunnel active at a time during testing; a full-tunnel VPN silently swallows a split-tunnel's traffic.

TRAP 3 — THE STALE DNS NAME (the root cause)

This was the real culprit. The ISP IP had silently rotated weeks earlier (205.147.16.103 → 77.171.22.64), but the DuckDNS auto-updater had never been finished — so hitachivantara.duckdns.org still pointed at the old, dead address. Every handshake from outside was being sent to a stranger who now held that IP. tcpdump was silent from mobile data not because of a firewall, but because the packets were never aimed at the right place.

The diagnostic that cracked it
curl ifconfig.me returned 77.171.22.64, but nslookup hitachivantara.duckdns.org 8.8.8.8 still returned 205.147.16.103. The mismatch was the whole answer. Always query a public resolver (8.8.8.8) — the local router (192.168.2.254) caches DNS and will keep showing the stale answer even after a flush, hiding the problem.

The signal of success

Once DuckDNS pointed at the right IP, the very first handshake from mobile data told the whole story in three tcpdump lines:

tcpdump -ni enp0s3 udp port 51822 — from mobile data
80.187.103.143.18733 > 192.168.2.91.51822: UDP, length 148   # handshake init (mobile IP)
192.168.2.91.51822 > 80.187.103.143.18733: UDP, length 92    # server RESPONSE
80.187.103.143.18733 > 192.168.2.91.51822: UDP, length 32    # confirmed; tunnel up

The source being a mobile address (not 192.168.2.x), a reply from the server (length 92), and wg show then reporting latest handshake with received bytes > 0 — that trio is the unambiguous "it works" signal. Received-bytes climbing is the proof replies get back, not just that packets leave.

Debugging checklist, in order

The one-sentence lesson
Most "WireGuard won't connect" mysteries on a home ISP are not the firewall or the keys — they are testing from inside the LAN or a stale dynamic-DNS name. Rule those two out first, from outside, querying a public DNS resolver.

12 Security posture

  • One UDP port exposed. WireGuard is silent to unauthenticated traffic — it does not respond to a port scan without a valid key, unlike an exposed web UI. This is the central reason to tunnel rather than port-forward SAM4H directly.
  • Never port-forward SAM4H (8080) or Cockpit (9090) to the internet. They carry known management credentials. Keep them behind the tunnel where the only internet-facing service is WireGuard's authenticated endpoint.
  • One keypair per device. Each gets its own [Peer] block and unique 10.99.99.x/32. Revoking a lost device = deleting its peer block.
  • Strong UI credentials. SAM4H and Cockpit are now reachable from any tunnel device, so keep those passwords strong.
  • Split tunnel means only lab ranges cross the VPN; your general browsing is unaffected and the tunnel carries only what it must.
The single rule
The internet sees exactly one thing: an authenticated UDP port that ignores everyone without a key. Everything else — the management UIs, the arrays, SSH — lives behind it. That is the whole security model, and it is a strong one.

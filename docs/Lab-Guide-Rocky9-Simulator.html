01 What integsim provides

integsim v10.2 is Hitachi's storage simulator. Each instance presents the two interfaces an operator and an automation stack actually talk to: a REST Configuration Manager surface (used by SAM4H and by the vspone_block modules) and a CCI command device reached over the network via IPCMD (used by raidcom/HORCM). It bundles its own CCI build (v01-76) internally, separate from the v01-88-03/03 CCI on the management node.

In this lab, four integsim VMs each emulate one VSP One B26 array with a distinct serial number, microcode A3-00-00/00, and 285184 MB of cache. The arrays start empty — no pools, no LDEVs, host groups present but with zero initiators — which is the intended blank canvas for automation and migration rehearsal.

Two surfaces, two auth paths
REST auth and CCI auth both use maintenance / raid-maintenance, but they validate differently. REST checks integsim's own user table; CCI validates against the OS user (extAuthFlg=1). A working REST surface with failing raidcom almost always means the OS password drifted — see §06.

02 On-disk layout

integsim installs under /root/integsim. The pieces that matter for building and operating an array:

PathPurpose
settings.txtTop-level config — serial number, ports, runtime options
setup.shOne-time generator; consumes settings + the config JSON
start.sh / stop.shBring the simulated array up / down
src/dkc-simulator/setup-dkc-simulator.shInner generator; the JSONGEN patch target
src/dkc-simulator/resource/generator/customed_config.jsonThe array personality definition

The simulator autostarts at boot from the simulator VM's own crontab: @reboot /root/integsim/start.sh. The management node never starts integsim — it only waits for the REST surface to answer.

03 customed_config.json

This file is the array's DNA. It defines the model identity, microcode string, cache size, controller ports, and the parity-group / drive layout that the generator turns into a running simulated array. The generator does not read it by default — it must be named explicitly (§04).

customed_config.json — shape (illustrative)json
{
  "model": "VSP One B26",
  "serialNumber": "810294",
  "microcodeVersion": "A3-00-00/00",
  "cacheMB": 285184,
  "controllerPorts": [ "CL1-A", "CL1-B", "CL2-A", "..." ],
  "parityGroups": [
    { "id": "1-1", "raidLevel": "RAID6", "driveType": "SAS" }
  ],
  "numberOfHbasPerHostGroup": 0
}
numberOfHbasPerHostGroup = 0
The shipped config creates host groups with zero registered initiators. That is why the facts export's All-HBA-WWNs tab is empty on a fresh array and every host group is flagged empty. To rehearse a migration with real WWN data, raise this value or register WWNs after the array is up (§07).

04 First-array install

Build the first array (serial 810294) by hand; the rest are clones of it. Three dependencies trip people up, in this order.

1

NGINX DEPENDENCY

integsim's bundled nginx links libcrypt.so.1, dropped from default Rocky 9.

sim VMroot
dnf install -y libxcrypt-compat
2

POINT THE GENERATOR AT THE CONFIG

The inner setup script defaults to a stock JSON. Patch it to use the B26 personality before running setup:

sim VMroot
sed -i 's/JSONGEN_FILENAME=.*/JSONGEN_FILENAME=customed_config.json/' \
    /root/integsim/src/dkc-simulator/setup-dkc-simulator.sh
3

SET SERIAL, RUN SETUP, START

sim VMroot
sed -i 's/^DKCSIM_SERIALNUM=.*/DKCSIM_SERIALNUM=810294/' \
    /root/integsim/settings.txt
EXT_IP=192.168.2.90 /root/integsim/setup.sh
/root/integsim/start.sh

EXT_IP is the bridged address the REST/IPCMD surfaces bind to. It must match the VM's own bridged IP.

Guest Additions (optional, for the shared folder)

If the VM mounts /mnt/vm_share, Guest Additions needs kernel headers matching the running kernel:

sim VMroot
dnf install -y gcc make kernel-devel-$(uname -r)

Verify the REST surface

mgmt noderoot
curl -sk -u maintenance:raid-maintenance \
  https://192.168.2.90/ConfigurationManager/v1/objects/storages \
  | jq -r '.data[0].serialNumber'
# -> 810294

05 Cloning the fleet

Arrays two through four are full VirtualBox clones of the first. A clone inherits two things that must be cleared before it will behave: the source's IP aliases and (on the mgmt side) its SSH host key.

Clear inherited aliases first
The 810294 image carried stale aliases (.93/.94/.95/.96) that caused SSH from mgmt to land on the wrong VM. Strip them before assigning the clone's own address.
freshly cloned sim VM — example: 840006root
# 1 - clear inherited aliases
nmcli con mod enp0s3 -ipv4.addresses 192.168.2.93/24
nmcli con mod enp0s3 -ipv4.addresses 192.168.2.94/24

# 2 - this clone's identity
nmcli con mod enp0s3 ipv4.addresses 192.168.2.93/24
hostnamectl set-hostname rocky9-sim-840006
sed -i 's/^DKCSIM_SERIALNUM=.*/DKCSIM_SERIALNUM=840006/' /root/integsim/settings.txt

# 3 - clones share a MAC seed: kill IPv6 dup-address noise
nmcli con mod enp0s8 ipv6.method disabled

# 4 - SSH from mgmt needs LEGACY crypto on a clean clone
update-crypto-policies --set LEGACY && systemctl restart sshd

# 5 - regenerate the array for the new serial + IP
EXT_IP=192.168.2.93 /root/integsim/setup.sh
/root/integsim/start.sh

On the mgmt node, drop any stale host key for a reused address:

mgmt noderoot
ssh-keygen -R 192.168.2.92

06 HORCM / IPCMD wiring

This is the part unique to a simulated array. A real VSP exposes a physical command device; integsim exposes a network command device that raidcom reaches through the IPCMD pseudo-path. The array side always listens on port 31001.

/etc/horcm1001.conf — mgmt nodefull
HORCM_MON
192.168.2.91    34001    1000    3000

HORCM_CMD
\\.\IPCMD-192.168.2.90-31001

HORCM_INST

HORCM_LDEV
  • HORCM_MON binds the mgmt node's own IP (192.168.2.91) on a unique monitor port (34001–34006). One port per instance, no overlap.
  • HORCM_CMD is the IPCMD path to the array: \\.\IPCMD-<array-ip>-31001. Not a device file, not a bare IP.
HORCM runs on mgmt only
The simulator VMs already bind 31001 for integsim's IPCMD listener, so HORCM cannot run there. All instances live on the management node. This is why the lab keeps the array side at 31001 and the monitor side at 34xxx — they are different roles on different hosts.

Instance mapping & the auto-assignment trap

SAM4H assigns the HORCM instance number when it registers an array, and re-increments on every delete/re-add. During the build, 840006 moved 1002→1005 and 845665 moved 1003→1006 when they were re-added to fix a cache problem.

SerialArray IPInstanceMON port
810294192.168.2.90100134001
845666192.168.2.94100434004
840006192.168.2.93100534005
845665192.168.2.92100634006

When the number changes, update three things in lockstep: the /etc/horcmNNNN.conf file, group_vars/vault.yml, and the instance list in lab-startup.sh. Then verify:

mgmt noderoot
for i in 1001 1004 1005 1006; do
  raidqry -l -IH${i} | grep -vE '^No|^$|^Group' | head -1
done
CCI auth uses the OS user
If raidcom login fails (and so SAM4H shows 0 Bytes cache), reset the OS password on the simulator: echo 'maintenance:raid-maintenance' | chpasswd, restart integsim, then re-trigger the SAM4H reload.

07 Host groups & WWNs

For migration rehearsal you want host groups that actually contain initiator WWNs, so the facts export captures meaningful login/registration data rather than an empty baseline.

Inspect what exists

mgmt node — via the array's instanceroot
# list host groups on a port
raidcom get host_grp -port CL1-A -I1001
# list registered HBA WWNs in a host group
raidcom get hba_wwn -port CL1-A-0 -I1001

Register an initiator WWN

mgmt noderoot
# add a WWN to host group 0 on CL1-A, then nickname it
raidcom add hba_wwn -port CL1-A-0 -hba_wwn 100000109b1a2b3c -I1001
raidcom set hba_wwn -port CL1-A-0 -hba_wwn 100000109b1a2b3c \
    -wwn_nickname srv1_p0 -I1001
How the export reads this
The facts toolchain captures WWNs two ways and merges them: logins seen by raidcom (get hba_wwn, source = login) and registered WWNs surfaced by the host-group module (source = registered). The same physical WWN may appear from both sources; the empty-host-group flag counts distinct WWNs, so it reads 1, not 2. A host group with no WWNs from either source is flagged empty (amber) — the migration signal for a placeholder with no initiators.

After registering WWNs, re-run the facts export: the All-HBA-WWNs tab fills, the host-group empty flag for that group clears, and the run-over-run diff shows the new WWN row highlighted green (added).

08 Driving the facts toolchain

With the fleet up, the export runs against all four arrays from the project root. It reads the array list from vault_arrays in the vault, gathers six module fact types plus raidcom WWN logins, and builds the workbook with a diff against the previous run.

mgmt node — project rootroot
cd /etc/ansible/Ansible_Simulator_Lab
bash scripts/run-facts-export.sh

# diff against a fixed baseline instead of last run:
cp -r exports/raw exports/baseline   # capture once
bash scripts/run-facts-export.sh --baseline exports/baseline

What lands where

  • exports/vsp_facts_<date>.xlsx — Summary, Changes, four per-array tabs, six All-<fact> tabs, and All-HBA-WWNs.
  • exports/csv/*.csv — flat mirror, one file per fact type plus hba_wwn.csv and summary.csv.
  • exports/history/<timestamp>/ — archived raw JSON (last 20 runs) used as the diff baseline.
  • /mnt/vm_share/vsp_facts_export/ — auto-copy for the Windows host (D:\vsp_facts_export).
Reading the diff colours
On the All-<fact> tabs: a fully green row is a newly added object; an amber cell is a changed field (old→new shown on the Changes tab); the host-group empty column is amber where a group has no initiators. Removed objects appear red on the Changes tab. A whole fact type showing as added+removed (never changed) means the diff key needs adjusting — see Troubleshooting F-2.

09 Lifecycle & persistence

Start / stop a single array

sim VMroot
/root/integsim/stop.sh
/root/integsim/start.sh   # REST surface ready ~30-60s later

Whole-lab startup order

The mgmt node's lab-startup.sh (cron @reboot) sequences the bring-up: network → SAM4H → wait for all four REST surfaces → start HORCM 1001/1004/1005/1006 → verify with raidqry. The simulator VMs bring integsim up themselves via their own crontab, so they are already booting when mgmt reaches the REST-wait loop. Full bring-up is about 90 seconds.

Snapshots vs the real backup

GitHub is the backup that matters
VirtualBox snapshots share a base disk and can fail together. Snapshot for convenience, but treat the Git repository as authoritative: a full rebuild from a clean Rocky 9 image to a working four-array lab is under an hour with the repo intact. Snapshot names in use: mgmt Rocky9-lab-vspb26-facts-export-may2026; changed sims sim-840006-may2026-v2, sim-845665-may2026-v2.
